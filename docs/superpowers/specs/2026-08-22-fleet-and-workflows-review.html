Design spec · fleet and workflows

Many agents at once,
in a window instead of a terminal.

Claude Code already ships four ways to parallelize work. What it doesn't ship is a GUI — rows hide after 30 seconds, four idle agents collapse into one line, and a 40-agent run is navigated with arrow keys. That's a terminal running out of room. Echo has a window.

Calls I made

Override any

These are judgment calls, not findings. Each one narrows the build; say the word and any of them flips.

The fleet is dispatched sessions only

claude agents --json also lists the nine terminal sessions you have open right now. Those aren't Echo's fleet and Echo can't drive them.

Bounds the list, not the parallelism. Also keeps the refresh loop to pure disk reads.

Talk to a live session by attaching, not adopting

claude attach runs in a terminal Echo owns, nested under the session's row — interactive, and nothing stops. Adopt is for when you want Echo's own thread UI, and it costs a stop.

No claude send exists. Attach is the only supported live turn.

Agent teams stay behind a default-off setting

The env var changes delegation for the whole session — any subagent Claude names becomes a teammate. Teams are experimental, with no resumption and a fixed lead.

Turn it on per dispatch, not per install.

Phase attribution is a substring match

The runtime never writes down which agent belongs to which phase. Echo finds the agent's prompt inside the script and takes the nearest preceding phase marker.

Fails toward Unattributed, never toward a wrong phase.

Workflows are observe-only in v1

Pause, resume, and restart-agent are keystrokes in the CLI's own view with no protocol equivalent. Stop works through the parent thread's cancel.

Deferred rather than faked.

New fleet crate, existing crates for UI

Same shape as listen: the crate is pure and testable, the wiring lives where the UI already is.

sidebar.rs is 8,591 lines. It gets rows, not readers.

Evidence

Probed, not assumed

Four questions were open before the spec. All four were answered by running them against Claude Code 2.1.239 on 22–23 August. Three changed the plan.

A dispatched session can't be attached over ACP while it runs

Verified

session/load against a live one is refused outright:

Session 91214c57… is currently running as a background agent (bg). Use claude agents to find and attach to it, or add --fork-session to branch off a copy.

After claude stop <id> the same call succeeds and replays the whole transcript as ordinary user_message_chunk / agent_message_chunk updates. The daemon owns a session while it runs; Echo adopts it once it doesn't.

Agent teams work in a dispatched session — and only there

Verified

They don't work over ACP. The adapter is built on @anthropic-ai/claude-agent-sdk, and Claude Code doesn't spawn teammates for Agent SDK sessions — a named subagent silently degrades to an ordinary subagent. Dispatching through the daemon with the experimental flag spawned a real one:

{ "agentId": "scout@session-3b6b4eb4", "name": "scout", "color": "blue",
  "agentType": "general-purpose", "model": "opus[1m]",
  "backendType": "in-process" }

Its transcript landed at <project>/<session>/subagents/agent-<id>.jsonl — the same directory and format Echo's subagent code already reads. Routing through the daemon is what unlocks teams; nothing else does.

A workflow announces itself on the wire

Verified Changed the plan

The launch arrives as a tool_call carrying _meta.claudeCode.toolName: "Workflow", then a tool_call_update whose rawInput.script is the entire script source — meta.phases and every agent(…, { label, phase }) call site included. The response carries the rest:

{ "status": "async_launched", "taskType": "local_workflow",
  "workflowName": "echo-alpha-beta", "runId": "wf_11e12c55-af7",
  "transcriptDir": "…/subagents/workflows/wf_11e12c55-af7",
  "scriptPath":   "…/workflows/scripts/echo-alpha-beta-wf_11e12c55-af7.js" }

No globbing, no guessing. Echo is handed the run id, the run directory, the script path, and the declared phases at launch.

The workflow journal is a resume cache, not a progress feed

Constrains the design

journal.jsonl holds only started / result records keyed by an opaque hash and an agentId. The sidecar is no help either:

agent-a4ba69c604ed54dc1.meta.json
  { "agentType": "workflow-subagent", "spawnDepth": 1 }   // no label, no phase

Verified identical on 2.1.239 and on an older run. Phase titles, labels, token totals, and elapsed time live in the CLI process's memory — which is why workflow resume only works inside one session. Everything per-agent is on disk; the phase each agent belongs to is not.

Architecture

Decided

New crate crates/fleet/, [lib] path = "src/fleet.rs". Every format the crate reads is a private Claude Code implementation detail, so the parsers are split out: they're the part most likely to break on a CLI upgrade and the part that must be exercised by fixtures.

FileHolds
src/fleet.rsThe Fleet entity, refresh loop, dispatch / stop / respawn / adopt, shared types
src/claude_home.rsPure parsers over ~/.claude. Path in, value out. No process spawning, no GPUI.
src/workflow.rsThe WorkflowRun model, script parsing, journal-to-transcript join, phase attribution

Echo writes no scheduler, no process manager, and no worktree logic. A per-user supervisor daemon already hosts the processes, restarts them on wake, upgrades them across versions, and puts each one in its own git worktree.

Part 1 · Fleet

Many real, parallel Claude Code sessions — each with its own process, git worktree, context, and transcript. The surface answers one question: which of these needs me?

Data planes

“Background” names only the absence of an attached terminal. A fleet session is a complete Claude session, not a subagent and not a reduced one.

PlaneSourceDocumented
Roster~/.claude/daemon/roster.json — workers keyed by short idNo
Detailjobs/<id>/state.json — state, detail, tokens, intent, linkScanPathNo
Activityjobs/<id>/timeline.jsonl — one record per state transitionNo
TranscriptlinkScanPath → projects/<cwd>/<session>.jsonlNo
Teamteams/session-<8 chars>/config.json — members[]Yes
Teammatesubagents/agent-<id>.jsonl + .meta.jsonNo
Taskstasks/<session uuid>/<n>.json — blocks, blockedByPartly

state.json is the richest and the least supported. It carries a written summary of what a session did — detail: "scout spawned and idle; instruction delivered" — that nothing else exposes. The tasks directory is keyed by session uuid, not by team name as the docs claim.

Types

pub struct FleetSession {
    pub short_id: String,           // "91214c57" — daemon id, also the jobs dir
    pub session_id: acp::SessionId, // full uuid; the ACP session id on adopt
    pub name: SharedString,
    pub state: FleetState,
    pub detail: Option<SharedString>, // the CLI's own written summary
    pub team: Option<Team>,
    pub tasks: Vec<Task>,
}

pub enum FleetState { Working, Blocked, Done, Failed, Stopped, Unknown(String) }

Unknown(String) is load-bearing. These formats are private and will gain states; an unrecognized value renders as itself and never panics.

Surface

  • One row per session: name, state, the CLI's own detail as subtitle, token count.
  • Grouped by working directory, matching the sidebar's existing project headers.
  • Teammates nest underneath, reusing the subagent row rendering that already exists — their .meta.json already carries name, type, model, and colour.
  • Blocked sessions sort to the top. That is the whole point of the surface.

Refresh is a 2-second poll of a directory of small JSON files while the section is expanded. Not a filesystem watch — state.json is rewritten on every transition and the debounce would cost more than the read.

Talking to one

A running session and a finished one admit different things, so there are three levels. All three are offered; none is a fallback for another failing.

LevelMechanismKeeps running
ReadTail the transcript at linkScanPathYes
Attachclaude attach <id> in a terminal Echo ownsYes
Adoptclaude stop, then ACP load_sessionNo

Attach

The answer to “can I talk to one of these?”, and the only level that is both interactive and non-destructive. There is no claude send or claude message — the CLI's hidden subcommands are exactly attach, logs, stop, respawn, and rm, so attach is the sole supported way to put a turn into a live session from outside it.

Echo is well placed for it: a Zed fork with a first-class terminal, whose sidebar already renders ListEntry::Terminal rows beside threads and subagents. Attaching opens a terminal entry nested under the session's own row, next to its teammates — the session's real interface, in place.

What it isn't: Echo's own thread UI. The attached view is Claude Code's TUI, so it gets no Echo transcript rendering, no narration, no voice. That's the honest trade for talking to a session that's still working, and it's why adopt still exists.

Adopt

Turns a session into a real Echo thread, and requires stopping it first — so it's explicit and never automatic.

Session stateOffered
done · stopped · failedOpen in Echo — stop (a no-op if already exited), then load_session
working · blockedAttach for a live conversation. Adopting is offered as Stop and open, with the stop named in the button.

Writing into a teammate's mailbox at teams/<team>/inboxes/<agent>.json would be a second route to a running session, and is rejected: Claude Code tells the recipient the message came from another agent rather than from you, so it can't approve a permission prompt or carry consent — and a malformed entry is a private-format corruption Echo would be causing. Attach delivers a real user turn; the mailbox delivers a nudge.

Part 2 · Workflows

One scripted run fanning out dozens of agents across phases. The surface answers a different question: what is this thing actually doing, and what did each agent find?

Lifecycle

StageSourceWhat Echo gets
LaunchACP tool_callA run exists — render a placeholder immediately
ScriptrawInput.scriptFull source: phases, and every agent() call with its label
IdentitytoolResponserunId, name, summary, transcriptDir, scriptPath
Progresstail journal.jsonlstarted / result per agent, in start order
Detailagent-<id>.jsonlPrompt, tool calls, result, usage, timestamps

The agentId in the journal is exactly the transcript filename, so that join is exact. Tokens and duration are computed from the transcript rather than read: sum usage across assistant records, take last-minus-first timestamp.

Phase attribution The one soft edge

The single thing not on disk. The script does carry it — phase('Alpha') statements sit next to the prompt each agent receives — and the script arrives on the wire. So Echo locates an agent's first prompt as a substring of the script source, then takes the nearest preceding phase marker. No JavaScript is parsed; it's a text search over a string Echo already holds.

// ponytail: substring match, nearest preceding phase marker. Fails for prompts
// built at runtime (template literals over a list); those render Unattributed.
// Upgrade path is asking Claude Code to persist label+phase in agent meta.json.

It fails cleanly and in a known direction. A dynamically-built prompt won't appear literally in the script, so its agent lands under Unattributed — a real group in the UI, never a wrong phase. Every agent is always shown; only its grouping is ever uncertain. Declared phases render whether or not anything has been attributed to them, so a run's shape is visible from the first frame.

Surface

A run belongs to the thread that launched it, so it nests there rather than in the fleet. In the thread, the bare Workflow tool-call row becomes a live run card. In the sidebar, the run nests under its thread. And the run view is the thing a terminal can't give you:

Selecting an agent opens its full transcript in the existing read-only viewer — its prompt, every tool call, its result. Reading four agents' reasoning side by side is the thing /workflows cannot do in a terminal.

Launching one

The adapter stamps origin: { kind: "human" } on prompts — the exact gate the ultracode keyword checks, verified in the adapter source. So workflows already run through Echo today, unsurfaced, and launching one needs no protocol work: a Run as workflow toggle on the message editor prefixes the prompt.

Failure modes

Standing risk

Every high-value field lives in an undocumented format. The mitigation isn't avoidance — it's that each surface degrades rather than breaks.

SituationBehavior
Daemon not runningEmpty fleet, not an error. The first dispatch starts it.
state.json schema changed by an upgradePer-field tolerance. Unparsable is None, unknown state is Unknown. A session with no state.json still renders from the roster.
Session stopped outside EchoNext poll reconciles. No cached authority.
Attach to a session whose process already exitedclaude attach fails and the terminal shows its error. Offer Open in Echo instead, which works on an exited session.
Adopt races the daemonload_session is the source of truth. If it returns the bg-guard error, the session didn't stop — report it and stay read-only.
Workflow tool call with no responseThe run is unlocatable. Render the tool call as it renders today and don't fabricate a run.
Agent transcript with no journal recordRender it as running. The journal lags the transcript, never leads it.
Prompt not found in the scriptUnattributed. Never dropped, never misfiled.
Echo restarts mid-runThe run directory is on disk and the thread persists — re-derive from transcriptDir, reread scriptPath.

A degraded fleet view still works from roster.json alone. A workflow with no attribution is still a complete list of agents with prompts, results, and transcripts. A schema break costs detail, not the feature.

Testing

Decided

Fixtures captured during the spike — a real state.json, roster.json, timeline.jsonl, team config, teammate meta, a two-agent journal, and the echo-alpha-beta script — go in crates/fleet/test_fixtures/. Every parser is a pure function over a path or a string, so the suite runs with no daemon, no network, and no Claude Code installed.

Cases that must hold

  • An unrecognized state renders Unknown and does not panic.
  • A session in the roster with no jobs/ directory still renders.
  • A task set with blockedBy produces the right blocked ordering.
  • Tail resumption from a byte offset does not re-emit records already seen.
  • An agent whose prompt appears verbatim attributes to the nearest preceding phase.
  • An agent whose prompt is absent attributes to None — and still renders.
  • A prompt appearing twice attributes to the first match and is flagged ambiguous, not silently split.
  • Tokens sum across multiple assistant records in one transcript.

Two end-to-end tests — one that actually dispatches, one that actually runs a workflow — sit behind RUN_FLEET_E2E=1 and stay out of CI. They cost tokens and need a real daemon.

Build order

Two shippable stops

Fleet and workflows are independent after step one. Either order, or both at once.

  1. claude_home.rs parsers, against fixtures. No UI.
  2. The Fleet entity and refresh loop.
  3. Sidebar fleet section, read-only: rows, grouping, blocked-first ordering.
  4. Read-only transcript view, reusing the existing tail.→ ships alone: a complete read-only fleet
  5. Dispatch, stop, respawn.
  6. Attach: a terminal entry running claude attach, nested under the session.
  7. Adopt.
  8. Teams: the env var at dispatch, members as nested rows, teammate transcripts.
  9. Task graph under a session.
  10. workflow.rs: script parsing, journal join, phase attribution. Fixtures only.

  13. Run view: phases, agents, per-agent transcript.→ ships alone: a complete workflow viewer

Appendix · Live preview

Idea captureSeparate document

Not part of the spec above and not scheduled. Captured here so it reviews alongside — the source of truth is 2026-08-23-live-preview-notes.md.

The app you're building, rendered inside Echo, with its console and network wired to the agent working on it.

The reframe

The point isn't the pixels. Your chrome-devtools and playwright MCP servers already let an agent drive a real Chrome — navigate, click, screenshot, read the console. That half is solved.

What's missing is that the agent's Chrome and your eyes are looking at different browsers. The agent drives an instance you can't see; you check the work in a window Echo knows nothing about. Every loop goes through alt-tab and a description.

One browser, two consumers: the agent drives it and reads its console, you watch the same pixels. The agent sees its own bugs is the payoff, and it only works if there's one instance.

What GPUI can't do — and why it doesn't matter here

There is no web content path in GPUI. No WKWebView, no wry, no CEF, no Servo. Zed draws every pixel itself to one GPU surface, and crates/gpui_web is GPUI compiled to WASM — the opposite direction. Embedding a real engine means overlaying a native view on that surface and fighting z-order, clipping, and occlusion, per platform.

A preview doesn't need one. Three things already in the tree make a cheaper route work:

Already presentWhy it matters
async-tungstenite = "0.31.0"The DevTools protocol is JSON-RPC over a WebSocket. The transport is already a dependency.
image, with decode featuresScreencast frames arrive as base64 JPEG.
RenderImage / ImageSourceDrawing a stream of frames is drawing an image, which GPUI already does well.

And there's direct precedent for embedding a foreign process and rendering its output inline: crates/repl runs a Jupyter kernel and draws the images it returns. A browser process is the same shape.

Roughly six CDP methods do it — Page.startScreencast for frames, Input.dispatch* for interaction, and Runtime.consoleAPICalled plus Network.responseReceived on the same connection, which is what makes one browser serve both consumers. No native view, no platform-specific code.

The ceiling, and the seam to a real browser

Screencast is compressed JPEG at roughly 10–20fps. Fine for did the layout break, what did the console say. Not fine for a surface you live in: no smooth scrolling, compression-blurred text, a round trip of input latency.

So the dromaki-shaped ambition — tabs, address bar, history — needs a natively composited engine, and this work doesn't get you there. What carries over is worth being precise about:

LayerReusable for a real browser
CDP client, session management, lifecycleYes — the control plane is the same
Console and network capture, agent wiringYes — the reason to build it at all
Input event translation (GPUI → CDP)Mostly — retargeted at a native view
Screencast frame transport and decodeNo — thrown away entirely

Build the preview knowing the frame transport is disposable and the control plane is not.

Open questions

  • Who owns the Chrome process — Echo, or the MCP server already launching one? Sharing is cheaper but couples Echo to that server's lifecycle.
  • Does the agent get the preview's console automatically, or on request? Piping every console.log into a turn is a context cost with no ceiling.
  • Headless with screencast, or headful offscreen? Headless renders some CSS differently — a preview that lies.
  • What happens on a dev-server restart, a port change, or a compile error page.
